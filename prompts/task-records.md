# Task Pulse 任务记录规范与初始化提示词

> 把本文件整段发给你的编码 Agent，或把下面的格式规范抄进项目的 `AGENTS.md` / `CLAUDE.md`。
> Task Pulse 是 DSH 的只读页签：它只读取 `docs/tasks/` 下的 Markdown，不会创建、修改或删除任何文件。

## 你的任务

先读懂当前项目，再在 `docs/tasks/` 下建立（或补齐）任务记录。要求：

1. 只写真实存在的事实。来源可以是 README、AGENTS.md、代码、Issue、提交记录或用户原话；找不到依据的写「待核实」，不要编造。
2. 如果三份文件已经存在，先读再补，不要覆盖历史记录。
3. 一个任务一个 `## ` 二级标题，字段用 `- 名称：值`，每个字段独占一行。
4. 所有文件内链接使用相对 `docs/tasks/` 的 Markdown 链接。
5. 不要动无关文件，不要执行 `git commit` / `git push`，除非用户明确要求。
6. 完成后告诉用户：打开 DSH 的「进度」页签并点“刷新”。

## 目录

Task Pulse 直接解析的三份文件：

- `docs/tasks/BOARD.md`：当前任务，唯一事实源
- `docs/tasks/DECISIONS.md`：已确认的决定
- `docs/tasks/progress.md`：按日期倒序的执行记录

可选文件（存在时用于体积/交接提示，不做结构解析）：

- `docs/tasks/task_plan.md`
- `docs/tasks/findings.md`
- `docs/tasks/ARCHIVE_INDEX.md`

建议再写一份 `docs/tasks/README.md`，说明本项目的维护规则：谁在什么时候更新哪份文件、什么情况需要用户确认。

## BOARD.md

```markdown
# 当前任务

最后核对 2026-11-13。维护方式见 [共同流程](README.md)。

## T-DEMO 示例任务

- 目标与完成条件：一句话说明做完的标准。
- 阶段：进行中
- 开始日期：2026-11-13
- 结束日期：未结束
- 已确认范围：用户已经确认的范围；没有就写「未确认」。
- 最近完成点：最近一次可验证的进展。
- 下一步：接手的人下一步做什么。
- 阻塞或待确认项：无
- 证据：[执行记录](progress.md#2026-11-13-demo)、[相关决定](DECISIONS.md#d-001)
- 更新时间：2026-11-13【DS操作】
```

规则：

- 标题必须是 `## T-<ID> <标题>`。ID 用大写字母、数字、短横线，例如 `T-DOCS-ARCH`，全局唯一。
- `阶段` 只能是：待办、进行中、待验证、待验收、暂缓、待核实。
- 日期用 `YYYY-MM-DD`；未开始写「未记录」，未结束写「未结束」。
- 以下十个字段必须齐全，且每个只出现一次：目标与完成条件、阶段、开始日期、结束日期、已确认范围、最近完成点、下一步、阻塞或待确认项、证据、更新时间。重复字段会被标记为错误，缺失字段会告警。
- 证据只放链接，不要放长段落。
- 一个任务结束后，把阶段改成「待验收」或从 BOARD 移除，并在 `progress.md` 留下结果。

## DECISIONS.md

```markdown
# 决策记录

<a id="d-001"></a>
## D-001 示例决定

- 状态：生效
- 决定与范围：决定了什么，边界在哪。
- 理由与替代方案：为什么这样定，放弃了什么。
- 确认依据：用户原话、日期或记录链接。
- 关联规则：[共同流程](README.md)。
- 取代关系：无。
```

规则：

- 标题必须是 `## D-<三位数字> <标题>`，建议从 `D-001` 连续编号。
- 锚点 `<a id="d-001"></a>` 必须紧贴标题上方，中间不能隔正文。
- `状态` 只能是：提议、待核实、生效、被取代、已废止。
- 六个字段必须齐全。
- 含糊的记录只能写「提议」；有明确用户原话和日期才写「生效」。
- 被新决定取代时，把旧记录状态改为「被取代」，并在新记录的「取代关系」里写 `D-xxx`。

## progress.md

```markdown
# 进度日志

<a id="2026-11-13-demo"></a>
## 2026-11-13 示例进展【DS操作】

- 做了什么：可复核的动作和结果。
- 验证：跑了什么命令、看到什么结果。
- 未完成 / 下一步：还没做的、交给谁。

<a id="2026-11-13-handoff-demo"></a>
## 2026-11-13 会话交接【DS操作】

- 范围：本次交接覆盖什么。
- 已完成：已经完成并可验证的事。
- 未完成 / 下一步：还没做的、下一步怎么做。
- 决定：相关的 D-xxx 或决定摘要。
- 风险 / 未验证：还没验证的部分。
- 接手入口：文件、命令或页面。
- 工作区状态：改动、提交、未提交情况。
```

规则：

- 标题以 `YYYY-MM-DD` 开头，执行者写在末尾的【】里，例如【DS操作】。不用日期开头的段落也能显示，但排序会靠后。
- 锚点紧贴标题上方，建议用 `日期-主题`，全文件唯一。
- 新的记录放最上面；同一主题的后续进展可以追加到原段落。
- 标题包含「会话交接」的段落会显示成交接卡，建议保留上面七个字段。
- 不要只写「继续优化」这类无法验证的话，写清文件、命令、结果和剩余工作。

## 链接与锚点

- 证据链接相对 `docs/tasks/`：`[说明](progress.md#2026-11-13-demo)`、`[项目说明](../README.md#...)`。
- 允许用 `../` 进入工作区其他目录，但不能逃出工作区；不要用绝对路径、`C:\` 或 `file://`。
- 外部链接（https）只显示文本，不会自动打开。
- 锚点就是标题上方 `<a id="..."></a>` 里的字符串。Task Pulse 点开证据时按它截取小节；没有锚点就显示整个文件。

## 维护节奏

- 开始一个任务：在 BOARD 加一条，阶段「进行中」，写清目标和完成条件。
- 有阶段性结果：更新「最近完成点」和「更新时间」。
- 需要用户拍板：阶段改「待核实」，把问题写进「阻塞或待确认项」。
- 用户确认后：写 `DECISIONS.md`，状态「生效」，再更新 BOARD。
- 收尾：把结果写进 `progress.md`；BOARD 里改为「待验收」或移除。
- 每次会话结束：如果涉及交接，补一段「会话交接」。

## 不要做

- 不要为了让页签好看而编造任务或决定。
- 不要在字段里写多行列表：插件只读取字段所在的第一行。
- 不要删除历史 progress 记录；要归档就追加归档说明。
- 不要在 `docs/tasks/` 之外另建一套任务记录，页签只认这个目录。

## 最小可用版本

如果项目刚开始，先建三份文件即可：

- `BOARD.md`：一条真实任务，十个字段齐全。
- `DECISIONS.md`：只有标题也可以；有决定时再按格式追加。
- `progress.md`：一条初始化记录，说明这次建立了什么。

示例只示意格式，不要原样复制任务内容。
